# Замеры

Спорные решения выбираются замером, а не по привычке. Правило выбора победителя записано до замера (в спецификации и в `src/contract_analyst/eval/experiments.py`, `RULES`). Поэтому результат нельзя подогнать под удобный ответ.

Здесь лежат только метрики. Тексты договоров, цитаты и эталон по реальным документам остаются в `data/` и в git не попадают.

## Данные

- **Эталон** — правильные ответы по 16 реальным документам: вид документа, реквизиты, условия, ставки, операции соглашений, цепочки, свёртка на две даты (2026-10-30 и 2027-02-01), кластеры и ловушки T1–T16. Его разметили два независимых ИИ-разметчика по инструкции `docs/golden_guide.md`, у каждого значения — дословная цитата и страница. 124 расхождения разобрал третий проход. Человек решил принципиальный вопрос семантики свёртки (соглашение меняет только названные пункты) и принял решения третьего прохода; выборочной проверки 20% значений не было. Эталон заморожен (sha256 в `data/golden/VERSION`).
- **Синтетический набор** — `synthetic/`: три вымышленные цепочки со своим эталоном. Задумывался как отложенный, но после первых прогонов на нём разбирались ошибки (выдуманные группы полей, НДС в шапке таблицы, штраф как ставка, формулировки операций), поэтому строго отложенным он больше не является. Все исправления — общие правила со своими тестами, а не правки под конкретные документы.
- **Синтетические сканы для E1** — страницы текстовых PDF, превращённые в сканы с поворотом, наклоном, размытием, шумом, JPEG-сжатием и пониженным разрешением. Эталон для них — исходный текстовый слой.

## Метрики

| Метрика | Что значит |
|---|---|
| `critical_accepted_wrong` | число принятых неверных значений критичных полей: номер, дата, ссылка на договор, дата вступления в силу, ставки, операции. Главная метрика: такая ошибка попадает в отчёт без предупреждения |
| `critical_coverage` | доля критичных значений эталона, которые агент принял и принял верно |
| `consolidation_acc` | доля точек сверки свёртки, совпавших с эталоном: по каждому договору и каждой дате — статус, набор ставок и каждое условие (88 точек на реальном наборе) |
| `consolidation_misses`, `consolidation_miss_list` | почему проиграна каждая точка свёртки: `status_wrong`; набор ставок — `rates_missing` (строки эталона нет), `rates_extra` (лишняя строка), `rates_period` (сумма и НДС те же, период другой); условие — `term_absent`, `term_conflict`, `term_glued` (склейка «старое; новое»), `term_different`. Одна точка может нести несколько причин |
| `rates_rows_acc` | доля строк ставок эталона, совпавших во всех наборах ставок: показывает прогресс, который скрывает «всё или ничего» точки набора |
| `golden_fold_acc`, `golden_fold_misses` | свёртка эталонных значений тем же кодом: меньше 1,0 при идеальных данных — расхождение кода свёртки или соглашения эталона, а не модели |
| `traps_passed` | сколько ловушек T1–T16 пройдено |
| `doc_kind_acc`, `chain_acc` | точность вида документа и состава цепочек |
| `json_valid_rate`, `tool_call_valid_rate` | задумывалась как доля ответов модели, разобравшихся с первого раза. **Оговорка:** `json_valid_rate` делит отказы извлечения (невалидный или обрезанный ответ) на новые вызовы модели в этом прогоне — это разные совокупности: при полном повторе из кэша получается 1,00, при частичном — любое число, даже отрицательное. Сравнивать варианты по ней нельзя; решения E3 и E4 по ней не принимались |
| `wall_seconds`, `llm_calls` | время прогона и число вызовов модели |
| `safety_net` | шаги, которые агент не сделал и которые доделала страховка в узле отчёта |

## Замеры и правила

| | Что сравнивается | Правило выбора |
|---|---|---|
| E1 | OCR: Tesseract 5 (rus) и PaddleOCR PP-OCRv5 eslav через RapidOCR, каждый без предобработки и с выравниванием плюс бинаризацией Sauvola | 1) точность критичных значений (номера, даты, суммы) при пороге уверенности, который даёт не меньше 99% точности принятых; 2) CER; 3) скорость и вес установки |
| E2 | Модель: Qwen3-8B и Qwen3-14B — **не проводился**: выбор модели оставлен заказчику (в ТЗ не задан), модель — параметр запуска | правило сохранено для заказчика: 1) отбрасываются модели с принятыми неверными критичными значениями, если есть модель без них; 2) наибольшая доля принятых верных (разница до 0,02 — ничья); 3) доля валидных JSON и вызовов инструментов; 4) меньше время; 5) при ничьей — модель меньше |
| E3 | Свёртка: операции применяет код или модель сводит условия сама | побеждает код, если модель не точнее больше чем на долю одного договора из пяти (0,2 доли точек); при ничьей — код, потому что каждый шаг кода прослеживается |
| E4 | Оркестрация: A — конвейер без агента, B — гибрид, C — полный агент, S — один вызов модели на папку | среди агентных B и C — больше пройденных ловушек, затем выше точность свёртки; при ничьей — B. A и S — точки отсчёта, показывают, что даёт агент |
| E5, E5b | Даты документа: пункты «вступает в силу», «действует до» читает отдельный запрос; «с даты подписания» — начало в день подписания (`e5_document_dates.md`) | qwen3:8b, сумма трёх наборов: неверных не больше 56, верных не меньше 148, ловушек не меньше 46, свёртка на каждом наборе не ниже, чем до изменения — **принято**: верных 148 → 170, неверных 66 → 52, ловушек 46 → 48 (наборы не слепые) |

## Как повторить

```bash
uv run contract-analyst experiment e2 --models ollama:qwen3:8b,ollama:qwen3:14b
uv run contract-analyst experiment e3
uv run contract-analyst experiment e4 --variants A,B,S
uv run contract-analyst eval golden runs/<id>
```

Каждый вариант запускается отдельно на каждую дату эталона (2026-10-30 и 2027-02-01), и каждая дата оценивается по своему прогону: так вариант со свёрткой моделью не получает за вторую дату результат свёртки кодом. Расхождения эталона со свёрткой кодом `golden check` показывает как «нужно решение» и не считает ошибками: иначе эталон подгонялся бы под код и замер E3 стал бы круговым.

Для замеров нужен эталон в `data/golden/golden.yaml`. Ответы модели кэшируются в `data/cache/llm.sqlite`, поэтому повторный прогон с тем же кодом и теми же промптами не вызывает модель заново.

## Результаты

- `e1_ocr.md` — OCR;
- `e2.md` — модель;
- `e3.md` — свёртка;
- `e4.md` — оркестрация;
- `final.md` — финальный прогон собранного пайплайна.


В `metrics.json` каждого прогона есть `git_commit` (код, на котором сделан прогон) и `llm_params` (параметры генерации), по ним видно, с какой конфигурацией записан ответ модели.
